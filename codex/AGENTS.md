# Global Development Guidelines

## 1. Core Principles

- KISS, YAGNI, DRY 원칙을 준수한다.
- 요구사항에 없는 기능이나 추상화를 추가하지 않는다.
- 기존 프로젝트의 아키텍처와 코딩 컨벤션을 존중한다.
- 프로젝트별 AGENTS.md 및 기술적 제약을 따른다.
- 불필요한 의존성, 설정, 문서 생성을 피한다.
- 사실과 추측을 구분하며 확인하지 않은 내용을 단정하지 않는다.
- 기본 응답 및 작업 보고는 한국어로 작성한다.

## 2. Development Workflow

### Simple Tasks

- 별도의 계획이나 스킬 호출 없이 직접 처리한다.
- 관련 파일만 수정하고 필요한 검증을 수행한다.

### Medium Tasks

- 영향 범위를 파악하고 간단한 구현 계획을 수립한다.
- 기존 구조를 활용하여 작은 단위로 구현한다.
- 변경 범위에 적합한 테스트를 수행한다.

### Complex Tasks

- 구현 전에 변경 대상, 접근 방식, 잠재적 위험을 정리한다.
- 중요한 아키텍처 및 비즈니스 의사결정은 사용자와 논의한다.
- 필요한 경우에만 설계 스킬과 서브 에이전트를 활용한다.
- 합의된 요구사항을 기준으로 단계적으로 구현한다.

## 3. Implementation

- 수정 전에 관련 코드와 의존 관계를 확인한다.
- 요청과 무관한 코드나 기존 사용자 변경 사항을 수정하지 않는다.
- 기존 구현을 재사용하되 불필요한 추상화를 만들지 않는다.
- 근본 원인을 해결하고 임시 우회 처리는 최소화한다.
- 데이터 정합성, 하위 호환성, 유지보수성을 고려한다.

## 4. Skill Usage

- Codex 자체의 기능을 우선 활용한다.
- 명확한 이점이 있거나 사용자가 요청한 경우에만 스킬을 사용한다.
- 유사한 목적의 스킬을 중복 실행하지 않는다.
- 전체 개발 워크플로를 모든 작업에 강제하지 않는다.

### Matt Pocock Skills

- grill-me: 불명확한 요구사항 및 아이디어 검증.
- grill-with-docs: 복잡한 도메인 설계 및 의사결정 기록.
- codebase-design: 모듈, 인터페이스 및 아키텍처 설계.
- improve-codebase-architecture: 기존 코드 구조 개선.
- diagnosing-bugs: 복잡한 오류의 근본 원인 분석.
- tdd: 핵심 비즈니스 로직 및 회귀 위험 검증.
- to-spec: 복잡한 요구사항의 구현 명세 작성.
- teach: 기술 및 코드 학습.
- handoff: 작업 컨텍스트 인계.
- writing-for-agents: 에이전트 지침 및 스킬 개선.

### Grilling Policy

- 구현 결과에 영향을 주는 핵심 의사결정만 질문한다.
- 코드에서 확인 가능한 사실은 직접 조사한다.
- 질문에는 가능한 경우 추천 답변과 기술적 근거를 포함한다.
- 쉽게 되돌릴 수 있는 사소한 결정은 합리적으로 처리한다.
- 핵심 질문 10개를 초과할 경우 추가 진행 여부를 확인한다.
- 충분한 합의가 이루어지면 인터뷰를 종료한다.

### Gstack

- gstack-review: 코드 리뷰 및 변경 위험 분석.
- gstack-qa: 브라우저 기반 QA 및 승인된 범위의 수정.
- gstack-qa-only: 코드 수정 없는 QA.
- gstack-browse: 브라우저 탐색 및 동작 확인.
- gstack-design-review: UI/UX 품질 검토.
- Gstack은 사용자가 명시적으로 요청할 때 사용한다.
- 다른 스킬과 동일한 검증 절차를 반복하지 않는다.

### Archify

- 아키텍처, ERD, 시퀀스 및 데이터 흐름 시각화에 활용한다.
- 사용자가 요청하지 않은 시각화 문서는 생성하지 않는다.

## 5. Context & Token Efficiency

- 작업 규모에 비례하여 탐색 및 검증 범위를 결정한다.
- 관련 파일, 심볼, 함수, 변경 사항을 중심으로 탐색한다.
- 코드베이스 전체를 불필요하게 반복해서 읽지 않는다.
- 이미 확인한 정보를 근거 없이 다시 조사하지 않는다.
- 대량의 로그와 명령어 출력은 필요한 부분만 확인한다.
- RTK를 활용하되 정확한 원본 출력이 필요하면 직접 확인한다.
- 불필요하게 장황한 계획서와 결과 보고서를 작성하지 않는다.
- 토큰 절약을 이유로 정확성과 필요한 검증을 희생하지 않는다.

## 6. Orca Collaboration Policy

- 기본적으로 메인 에이전트가 직접 작업한다.
- 사용자 요청 또는 명확한 이점이 있을 때만 작업을 위임한다.
- 백엔드, API, DB, 비즈니스 로직은 Codex를 우선한다.
- 프론트엔드, UI/UX 구현은 Antigravity를 우선한다.
- 코드 리뷰 및 Gstack QA는 Codex를 우선한다.
- Orca 작업 인계는 orca-cli를 활용한다.
- 결과 회수가 필요한 Orca 작업 위임은 orchestration을 활용한다.
- Orca를 사용할 수 없는 환경에서는 현재 에이전트가 직접 처리한다.
- 위임 시 목표, 작업 범위, 제약 조건, 완료 기준을 명시한다.
- 병렬 작업은 파일 소유권과 작업 범위를 분리한다.
- 합의된 API 계약과 설계 명세를 임의로 변경하지 않는다.
- 불필요한 다중 에이전트 호출과 중복 작업을 방지한다.
- 결과 통합 및 최종 검증은 메인 에이전트가 담당한다.

## 7. Verification

- 변경 범위에 적합한 테스트와 정적 분석을 수행한다.
- 관련되는 경우 다음 항목을 검토한다.
  - 트랜잭션 및 롤백
  - 동시성 및 경쟁 상태
  - 예외 처리
  - 데이터 정합성
  - 보안 및 접근 제어
  - 성능 및 회귀 위험
- 검증하지 못한 항목은 명확하게 알린다.
- 작업 완료를 주장하기 전에 검증 결과를 확인한다.

## 8. Learning Support

- 중요한 설계 결정과 기술적 선택의 이유를 설명한다.
- 복잡한 비즈니스 로직은 데이터 흐름과 핵심 동작을 요약한다.
- 의미 있는 트레이드오프와 대안을 설명한다.
- 사용자 요청 시 이해도를 점검하는 질문을 제공한다.
- 단순 작업에는 불필요하게 긴 이론 설명을 추가하지 않는다.

## 9. MCP & Security

- 라이브러리 API나 버전별 동작이 불확실하면 Context7을 사용한다.
- 브라우저 검증은 Chrome DevTools, Orca 또는 Gstack 중 적합한 도구를 선택한다.
- 동일한 목적의 도구를 중복 호출하지 않는다.
- 브라우저 검증은 승인된 개발 및 테스트 환경에서만 수행한다.
- 사내 기밀, 인증 토큰, 고객 데이터를 외부 서비스에 전달하지 않는다.
- 운영 환경 변경, 외부 전송, 파괴적 작업은 사전 승인을 받는다.
- MCP를 통한 상태 변경 작업은 사전 승인을 받는다.
- 사용자 승인 없이 보안 정책과 실행 권한을 완화하지 않는다.

## 10. Reporting

- 변경 파일, 핵심 변경 사항 및 변경 이유
- 수행한 테스트 및 검증 결과
- 확인되지 않은 사항 및 잠재적 위험

작업 규모에 따라 간결하게 보고한다.
